1. The big picture

The browser (frontend) never talks to the database directly — it always asks the Express server, and only the server reads/writes the database. That's why passwords and business rules live on the backend, never in code shipped to the browser.

2. Logging in — the JWT flow

flowchart LR
  A["User submits
email + password"] --> B["bcrypt.compare
checks password"] --> C["jwt.sign
{ userId }, secret"] --> D["httpOnly cookie
ic_session sent back"]

Password: never stored as text — only a one-way bcrypt hash. Even a stolen database can't be reversed back into passwords.

JWT: a signed token holding just the user's id. Signed = server can prove it made it; nobody can forge one without the secret key.

Why not a session table? Verifying a JWT is pure math (check the signature) — no database lookup needed on every request. One less table to keep in sync.

3. Every request after login

flowchart LR
  A["Request comes in"] --> B{"Cookie valid?"}
  B -- No --> C["401 — logged out"]
  B -- Yes --> D["req.userId set
→ route runs"]

The browser attaches the cookie automatically to every request (frontend just sets credentials: 'include'). No token handling in frontend code at all.

requireAuth blocks the route if the cookie's missing/invalid. optionalAuth never blocks — used for read-only pages. Logout just deletes the cookie — nothing to clean up server-side.

4. The database

flowchart LR
  users --> posts
  users --> comments
  users --> votes
  posts --> comments
  posts --> votes
  comments --> comment_reactions
  users --> watchlist_items

One PostgreSQL database (backend/schema.sql), tables linked by IDs. No ORM — hand-written SQL with $1,$2 placeholders (blocks SQL injection). No migration tool — CREATE TABLE IF NOT EXISTS runs on every startup. Counts (votes, reactions) are computed live with SUM(), never stored as a running number.

  • features/ — auth/, discussions/, news/, portfolio/
